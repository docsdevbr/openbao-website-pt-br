# Modelo de segurança

Devido à natureza do OpenBao e à confidencialidade dos dados que ele gerencia,
o modelo de segurança do OpenBao é crucial.
O objetivo geral do modelo de segurança do OpenBao é garantir
[confidencialidade, integridade, disponibilidade, responsabilidade e autenticação](https://en.wikipedia.org/wiki/Information_security).

Isso significa que os dados em repouso e em trânsito devem estar protegidos
contra interceptação ou adulteração.
Os clientes devem ser devidamente autenticados e autorizados para acessar dados
ou modificar políticas.
Todas as interações devem ser auditáveis e rastreáveis de forma exclusiva até a
entidade de origem, e o sistema deve ser robusto contra tentativas intencionais
de burlar seus controles de acesso.

# Modelo de ameaças

A seguir, apresentamos as diversas partes do modelo de ameaças do OpenBao:

- **Interceptação de qualquer comunicação do OpenBao.**
  A comunicação do cliente com o OpenBao deve ser protegida contra
  interceptação, assim como a comunicação do OpenBao com seu backend de
  armazenamento ou entre os nós do cluster OpenBao.

- **Adulteração de dados em repouso ou em trânsito.**
  Qualquer adulteração deve ser detectável e fazer com que o OpenBao interrompa
  o processamento da transação.

- **Acesso a dados ou controles sem autenticação ou autorização.**
  Todas as requisições devem ser processadas pelas políticas de segurança
  aplicáveis.

- **Acesso a dados ou controles sem responsabilização.**
  Se o registro de auditoria estiver habilitado, as requisições e respostas
  devem ser registradas antes que o cliente receba qualquer material secreto.

- **Confidencialidade dos segredos armazenados.**
  Quaisquer dados que saiam do OpenBao para repousar no backend de armazenamento
  devem estar protegidos contra interceptação.
  Na prática, isso significa que todos os dados em repouso devem ser
  criptografados.

- **Disponibilidade de material secreto em caso de falha.**
  O OpenBao suporta a execução em uma configuração de alta disponibilidade para
  evitar a perda de disponibilidade.

Os seguintes itens não são considerados parte do modelo de ameaças do OpenBao:

- **Proteção contra o controle arbitrário do backend de armazenamento.**
  Uma pessoa atacante que possa realizar operações arbitrárias contra o backend
  de armazenamento pode comprometer a segurança de diversas maneiras difíceis ou
  impossíveis de evitar.
  Por exemplo, uma pessoa atacante poderia excluir ou corromper todo o conteúdo
  do backend de armazenamento, causando perda total de dados para o OpenBao.
  A capacidade de controlar as leituras permitiria que uma pessoa atacante
  criasse um snapshot em um estado conhecido e revertesse as alterações de
  estado se isso lhe fosse vantajoso.

- **Proteção contra o vazamento da existência de material secreto.**
  Uma pessoa atacante que possa ler do backend de armazenamento pode observar
  que o material secreto existe e está armazenado, mesmo que seja mantido em
  sigilo.

- **Proteção contra análise de memória de uma instância OpenBao em execução.**
  Se uma pessoa atacante for capaz de inspecionar o estado da memória de uma
  instância OpenBao em execução, a confidencialidade dos dados poderá ser
  comprometida.

- **Proteção contra falhas em sistemas ou serviços externos usados pelo
  OpenBao.**
  Alguns métodos de autenticação ou mecanismos de segredos delegam operações
  sensíveis a sistemas externos ao OpenBao.
  Se uma pessoa atacante conseguir comprometer credenciais ou explorar uma
  vulnerabilidade nesses sistemas externos, a confidencialidade ou a integridade
  dos dados poderá ser comprometida.

- **Proteção contra plugins maliciosos ou execução de código no host
  subjacente.**
  Se uma pessoa atacante conseguir executar código ou obter privilégios de
  gravação no host subjacente, a confidencialidade ou a integridade dos dados
  poderá ser comprometida.

- **Proteção contra falhas em clientes ou sistemas que acessam o OpenBao.**
  Se uma pessoa atacante conseguir comprometer um cliente OpenBao (por exemplo,
  sistema, navegador) e obter as credenciais OpenBao desse cliente, ela poderá
  acessar o OpenBao com o nível de privilégio associado a esse cliente.

- **Proteção contra pessoas administradoras do OpenBao que fornecem dados de
  configuração vulneráveis ou maliciosos.**
  Quaisquer dados fornecidos como valores de configuração para os endpoints
  administrativos do OpenBao (por exemplo, configurações de
  [engines de segredos](../secrets/index.mdx)) ou arquivos de configuração do
  OpenBao devem ser validados.
  Se uma pessoa atacante conseguir gravar na configuração do OpenBao, a
  confidencialidade ou integridade dos dados poderá ser comprometida.

## Visão geral das ameaças externas

A arquitetura do OpenBao é composta por três sistemas distintos:

- Cliente: Comunica-se com o OpenBao por meio de uma API.
- Servidor: Fornece uma API e atende às requisições.
- Backend de armazenamento: Utilizado pelo servidor para ler e gravar dados.

Não há confiança mútua entre o cliente e o servidor do OpenBao.
Os clientes usam [TLS](https://en.wikipedia.org/wiki/Transport_Layer_Security)
para verificar a identidade do servidor e estabelecer um canal de comunicação
seguro.
Os servidores exigem que o cliente forneça um token para cada requisição, o qual
é usado para identificar o cliente.
Um cliente que não fornece seu token só pode fazer requisições de login.

Todo o tráfego entre servidores em instâncias do OpenBao em um cluster usa TLS
com autenticação mútua para garantir a confidencialidade e a integridade dos
dados em trânsito.
Os nós são autenticados antes de ingressarem no cluster por meio de um
[desafio de desbloqueio](../concepts/integrated-storage/index.mdx#vault-networking-recap).

Os backends de armazenamento usados pelo OpenBao também são projetados como não
confiáveis.
O OpenBao usa uma barreira de segurança para todas as requisições feitas ao
backend.
A barreira de segurança criptografa automaticamente todos os dados que saem do
OpenBao usando uma cifra de 256 bits
[Advanced Encryption Standard (AES)](https://en.wikipedia.org/wiki/Advanced_Encryption_Standard)
no
[Galois Counter Mode (GCM)](https://en.wikipedia.org/wiki/Galois/Counter_Mode)
com nonces de 96 bits.
O nonce é gerado aleatoriamente para cada objeto criptografado.
Quando os dados são lidos da barreira de segurança, a tag de autenticação GCM é
verificada durante o processo de descriptografia para detectar qualquer
adulteração.

Dependendo do backend utilizado, o OpenBao pode se comunicar com o backend por
meio de TLS para fornecer uma camada adicional de segurança.
Em alguns casos, como em um backend de arquivos, isso não se aplica.
Como os backends de armazenamento não são confiáveis, uma pessoa invasora só
obteria acesso a dados criptografados, mesmo que a comunicação com o backend
fosse interceptada.

## Visão geral das ameaças internas

Dentro do sistema OpenBao, uma preocupação crítica de segurança é uma pessoa
invasora tentar obter acesso a material secreto ao qual não está autorizada.
Isso representa uma ameaça interna se a pessoa invasora já tiver permissão para
algum nível de acesso ao OpenBao e for capaz de se autenticar.

Quando um cliente se autentica pela primeira vez no OpenBao, um método de
autenticação é usado para verificar a identidade do cliente e retornar uma lista
de políticas de ACL associadas.
Essa associação é configurada pelas pessoas operadoras do OpenBao
antecipadamente.
Por exemplo, pessoas usuárias do GitHub na equipe de "engenharia" podem ser
mapeadas para as políticas "engenharia" e "ops" do OpenBao.
O OpenBao então gera um token de cliente, que é um valor serializado gerado
aleatoriamente, e o mapeia para a lista de políticas.
Esse token de cliente é então retornado ao cliente.

Em cada requisição, um cliente fornece esse token.
O OpenBao o utiliza para verificar se o token é válido e não foi revogado ou
expirou, e gera uma ACL com base nas políticas associadas.
O OpenBao usa uma estratégia de negação estrita por padrão.
Isso significa que, a menos que uma política associada permita uma determinada
ação, ela será negada.
Cada política especifica um nível de acesso concedido a um caminho no OpenBao.
Quando as políticas são mescladas (se várias políticas estiverem associadas a um
cliente), o nível de acesso mais alto permitido é usado.
Por exemplo, se a política "engenharia" permitir acesso de leitura/atualização
ao caminho "eng/" e a política "ops" permitir acesso de leitura ao caminho
"ops/", a pessoa usuária obterá a união dessas políticas.
A política é correspondida usando a política definida mais específica, que pode
ser uma correspondência exata ou o padrão glob de correspondência de prefixo
mais longo.
Consulte a [sintaxe de política](../concepts/policies.mdx#policy-syntax) para
obter mais detalhes.

Certas operações são permitidas apenas por pessoas usuárias "root", que é uma
política distinta integrada ao OpenBao.
Isso é semelhante ao conceito de um usuário root em um sistema Unix ou um
administrador no Windows.
Nos casos em que os clientes recebem tokens root ou são associados à política
root, o OpenBao oferece suporte ao conceito de privilégio "sudo".
Como parte de uma política, as pessoas usuárias podem receber privilégios "sudo"
para determinados caminhos, permitindo que realizem operações sensíveis à
segurança sem obter acesso root global ao OpenBao.

Por fim, o OpenBao suporta o uso de uma
[regra de duas pessoas](https://en.wikipedia.org/wiki/Two-person_rule) para
desbloqueio usando a
[técnica de compartilhamento secreto de Shamir](https://en.wikipedia.org/wiki/Shamir's_Secret_Sharing).
Quando o OpenBao é iniciado, ele começa em um estado _selado_.
Isso significa que a chave de criptografia necessária para ler e gravar no
backend de armazenamento ainda não é conhecida.
O processo de desbloqueio requer o fornecimento da chave raiz para que a chave
de criptografia possa ser recuperada.
O risco de distribuir a chave raiz é que uma única pessoa atacante maliciosa com
acesso a ela pode descriptografar todo o OpenBao.
Em vez disso, a técnica de Shamir nos permite dividir a chave raiz em várias
partes.
O número de compartilhamentos e o limite necessário são configuráveis, mas por
padrão, o OpenBao gera 5 compartilhamentos, dos quais 3 devem ser fornecidos
para reconstruir a chave raiz.

Ao usar uma técnica de compartilhamento secreto, evitamos a necessidade de
depositar confiança absoluta na pessoa detentora da chave raiz e evitamos
armazená-la completamente.
A chave raiz só pode ser recuperada reconstruindo os compartilhamentos.
Os compartilhamentos não são úteis para fazer requisições ao OpenBao e só podem
ser usados para desbloqueio.
Uma vez aberto, os mecanismos ACL padrão são usados para todas as requisições.

Para fazer uma analogia, um banco coloca caixas de depósito de segurança em um
cofre.
Cada caixas de depósito de segurança tem uma chave, enquanto a porta do cofre
tem uma combinação e uma chave.
O cofre é revestido de aço e concreto, de modo que a porta é a única entrada
prática.
A analogia com o OpenBao é que o criptossistema é o aço e o concreto que
protegem os dados.
Embora fosse possível cavar um túnel através do concreto ou usar força bruta
para descobrir as chaves de criptografia, isso seria extremamente demorado.
Abrir o cofre do banco exige dois fatores: a chave e a combinação.
Da mesma forma, o OpenBao exige que várias partes sejam fornecidas para
reconstruir a chave raiz.
Uma vez aberto, cada caixa de depósito de segurança ainda exige que a pessoa
proprietária forneça uma chave e, similarmente, o sistema ACL do OpenBao protege
todos os segredos armazenados.
